## 一、问题现象

用户明确要求执行开发任务时，AI 偶发直接回复：

- 当前会话没有终端执行入口。
- 当前会话没有文件编辑工具。
- 因此无法继续开发。

同一台电脑上的 Codex CLI 后续也实时复现了工具清单消失和原始 `<thinking>` 泄漏。因此 AgentDesk Renderer 已基本排除为工具缺失的根因。

## 二、必须区分的三种状态

1. **系统真的没有工具**：app-server 没有建立执行环境，或工具运行时启动失败。
2. **工具存在但调用失败**：能看到 `commandExecution` 或 `fileChange`，但执行结果失败。
3. **模型误以为没有工具**：没有尝试调用工具，直接用文字声称“没有工具”。

当前已找到的明确案例属于第 3 种，不属于 Windows 权限不足，也不属于普通命令执行失败。

- 失败前后使用的是同一个 AgentDesk 主进程和同一个 Codex app-server 生命周期。

### F4：AgentDesk 与 CLI 的运行方式不同

- AgentDesk 启动一个长期运行的 `codex app-server`，多个 Codex 会话通过它通信。
- Codex CLI 黑窗口通常直接运行一个前台交互会话，生命周期和并发情况更简单。
- OpenAI 官方文档说明，同一 app-server 进程中的线程会共享 Code Mode host 连接。这是官方支持的结构，本身不能直接判定为错误。

- Codex CLI 版本：`0.147.0`，当前 npm 最新版本也是 `0.147.0`。
- 当前 `model_provider = "custom"`，协议为 Responses API。
- 因此还必须区分：工具状态是在 Codex app-server 内丢失，还是自定义网关处理请求时出现异常。

### F10：预压缩 T1R 连续三轮正常

- 连续三次注入 225,000 个词。
- 每次都先独立调用 `thread/compact/start`，等待压缩 Turn 完成，再发起要求执行 `Get-Location` 的用户 Turn。
- 三轮压缩后都产生完整、成功的 `commandExecution`。
- 原始结果：`build/logs/codex-tool-availability-2026-08-11T08-37-07-092Z.json`。

结论：**预压缩是目前有效的客户端规避方案**；它不改变模型能力，但能避开“用户 Turn 内自动压缩后偶发不调用工具”的高风险路径。它仍是缓解措施，不等于修复中转站或上游生成端。

压缩请求本身会出现一个空的 `additional_tools` 项，这是压缩专用采样；紧随其后的用户 Turn 会重新带上完整工具，不能把压缩请求误当成用户请求。

- **已排除“Codex CLI/app-server 在异常用户 Turn 中漏发工具定义”。**

- 仅靠客户端捕获还不能继续区分“中转站转换代码丢失/改写工具”与“中转站背后的模型偶发不遵守工具要求”；需要中转站服务端记录它实际转发给模型的请求才能二次归责。
- 本次线级复现没有出现 `<thinking>` 标签，因此尚不能用同一份捕获结果判定 `<thinking>` 是中转站生成、上游模型生成还是 Codex 显示错误。

## 七、判定规则

- T0 失败：先停止后续测试，说明基础工具链本身不稳定。
- T0 成功、T1 失败：重点定位压缩后的工具重建。
- T1 成功、T3 失败：重点定位共享 app-server 的并发状态。
- T1、T2、T3 成功而 T4 失败：重点定位长上下文中的 Turn 内自动压缩。
- 自定义 Provider 失败而官方 Provider 成功：根因主要在自定义网关或它与 Codex 的兼容层。
- 原生 app-server 全部成功而 AgentDesk 真实链路失败：根因主要在 AgentDesk 请求、恢复或并发管理。

## 八、预期根治方向

只有对照测试支持后才实施对应方案：

1. AgentDesk 在接近上下文上限时先调用 `thread/compact/start`，等待压缩 Turn 完成，再提交用户消息，作为已验证的客户端缓解措施。
2. 对明确要求执行却没有任何工具 Item 的 Turn 增加结构化诊断，不把模型文字“没有工具”当成工具运行时事实。
3. 把本次脱敏线级证据交给中转站，要求服务端确认异常请求中的 `additional_tools` 是否完整转发给实际模型。
4. 如果中转站服务端确认转发时丢失或改写，修复 Responses `additional_tools` 和 Code Mode 自定义工具兼容。
5. 如果中转站确认完整转发，则需要更换或修复其背后的模型服务，并用同一长上下文测试重复验证。

## 九、验收标准

- 长会话发生压缩后，下一条明确要求执行只读命令的请求能产生 `commandExecution`。
- 两个 Codex 会话并发工作，其中一个发生压缩时，另一个及压缩后的会话均能继续使用工具。
- 工具链真的异常时，AgentDesk 显示结构化错误和恢复结果，不允许 AI 用普通回复伪装成正常完成。
- 新增真实 Provider 回归覆盖“压缩后执行”和“共享 app-server 并发”场景。
- 不影响 Claude Provider，不扩大 IPC 权限，不取消现有容量和安全限制。

## 十、官方依据

  - `thread/compact/start` 会立即返回，压缩过程通过标准 Turn/Item 事件流报告。
  - 压缩使用 `contextCompaction` 的 `item/started` 和 `item/completed` 生命周期。
  - 命令执行使用结构化 `commandExecution` Item。
