# AgentDesk 代码审查与优化路线图

## 文档定位

本文档是 AgentDesk 后续结构优化、性能优化和工程治理的执行基线。

- 新功能仍以用户需求为准，但实现方式不得破坏本文档定义的代码边界和安全边界。
- 优化任务必须按优先级推进；没有完成前置质量门禁，不进行大范围重构。
- 每次只做一个可独立验证的改动，不进行一次性重写。
- 代码、测试和真实 Electron 行为是实现事实；本文档负责记录问题、目标、顺序和验收标准。
- 任务完成并通过验证后，才可把状态从“待开始”改为“已完成”。

## 必须保留的边界

所有优化都必须保留以下现有设计，不能以“重构”为理由削弱：

1. Codex 和 Claude 的 Backend、Worker、事件、Query 代次和退出清理保持隔离。
2. Renderer 不获得 Node、文件系统或子进程权限；所有桌面能力继续通过受控 preload 和 IPC。
3. Provider 差异继续集中在 Backend、Provider 注册表和事件适配器，不散落到普通组件。
4. 工作区、会话、审批、附件和 Query 必须继续做归属校验。
5. 外部链接、本地路径、图片内容、更新包和 Claude 签名校验不得放宽。
6. 原始事件、消息、活动、附件和偏好文件的容量上限不得取消。
7. 不引入新的状态管理框架、路由或 UI 组件库，除非现有方案已无法满足明确需求并经过单独评估。
8. 不为了减少文件行数制造无意义的转发层；拆分后的模块必须拥有清晰职责和可独立测试的接口。

## 开发约束

后续新增或修改功能时，严格遵守以下规则：

1. 新的会话生命周期、队列或 Provider 事件逻辑不得继续直接堆入 `App.tsx`，应进入对应 controller/hook 或 Provider 适配器。
2. 新的窗口、更新、进程或 IPC 业务不得继续直接堆入 `main.ts`，应进入独立主进程模块，由入口负责组装。
3. 具体组件不得直接调用 Agent Bridge；请求继续经过统一的会话请求路径。
4. 新增 Provider 时，不允许在通用组件中增加成片的 `provider === ...` 判断。
5. 新依赖必须说明用途、包体积、Electron 兼容性和是否能用现有依赖完成。
6. 修改共享状态或协议时，必须补充乱序、迟到响应、Query 失效和 Provider 退出场景测试。
7. 涉及真实 Provider、IPC、进程、附件、审批或更新的修改，必须做真实 Electron 验证。
8. 重构任务默认不改变用户行为；如需同时改变行为，必须拆成独立步骤和独立验收。
9. 不通过提高 Vite 警告阈值、跳过测试或删除容量限制来“解决”指标问题。
10. 每完成一个任务，都要更新本文档的状态、实际结果和剩余风险。

## 第一阶段：质量门禁

### OPT-001 普通提交和 PR CI

问题：当前 `.github/workflows/release.yml` 只在 `v*` Tag 推送时运行。普通开发提交可能直到正式发布才暴露编译或测试失败。

实施要求：

- 新建独立验证工作流，不把验证和发布混在同一个 job。
- 至少覆盖 `develop` 的 push 和 pull request。
- 使用项目声明的 Node/npm 版本和 `npm ci`。
- 执行主进程编译、Renderer 类型检查、Vite 构建和全部 Node 测试。
- 不在普通验证工作流中打安装包、创建 Release 或上传发布产物。

验收：故意制造一个类型错误时 CI 必须失败；恢复后 CI 必须通过。

当前结果（2026-08-09）：

- 已新增 `.github/workflows/validate.yml`，覆盖 `develop` push 和 pull request。
- 工作流权限为 `contents: read`，只安装依赖并执行完整构建测试，不打包、不发布。
- 本地完整构建通过：98 项测试通过，1 项因 Windows 符号链接权限跳过，0 失败。
- 尚未推送，远端 Actions 的失败/恢复验收待后续正常提交或 PR 完成。

### OPT-002 消除重复构建

问题：`postinstall` 当前执行完整 `npm run build`，而 `npm run package` 会再次执行完整构建。

实施要求：

- `postinstall` 只完成依赖安装阶段真正需要的 Electron 准备工作。
- 完整构建由 `build`、CI 或打包命令显式触发。
- Release 仍必须在打包前完整执行构建和测试。
- 本地首次安装后不能出现 Electron 二进制缺失。

验收：Release 日志中只出现一次完整测试；本地干净安装、编译和启动均通过。

当前结果（2026-08-09）：

- `postinstall` 已只保留 Electron 安装，不再隐式调用 `npm run build`。
- Validate 工作流使用普通 `npm ci` 后显式执行一次 `npm run build`。
- Release 工作流保持 `npm ci` 后执行 `npm run package`，完整构建只由 `package` 触发一次。
- 依赖刷新日志确认 `postinstall` 只执行 Electron 安装，约 1 秒结束；构建预检通过。
- 远端干净安装和 Release 日志的最终验收待后续正常提交或 PR 完成。

### OPT-003 真实 Electron 核心回归

问题：现有测试对状态和安全边界覆盖较好，但 SDK 初始化、Electron IPC 和真实进程行为仍主要靠人工验证。本次“加载模型”问题就是纯单测难以发现的真实链路问题。

首批场景：

- 新建 Codex 会话并发送首条消息。
- 新建 Claude 会话，首条消息前切换模型，发送后模型仍一致。
- 停止运行中的回合并确认状态收敛。
- 关闭运行中的 Tab，确认 Query 和子进程释放。
- 一个 Provider 退出时，另一个 Provider 会话不受影响。
- 恢复历史会话并继续发送。

验收：场景可重复运行，失败时保留明确日志；不得依赖人工固定等待时间。

当前结果（2026-08-09）：

- 新增 `scripts/electron-regression.ps1` 作为统一入口；脚本通过项目原生 `npm run dev` 启停开发实例，Electron 操作只走 Playwright Skill wrapper，并在结束时自动 detach、停止自己创建的进程树。
- 新增 `scripts/electron-core-smoke.js`，默认使用受控 Claude 生命周期夹具，已验证真实 Bridge、首条消息前模型选择、任务中断、Provider 退出隔离、错误归属和运行中 Tab 关闭后的 Query/进程树释放，共 6 条。
- 新增 `scripts/electron-live-provider-smoke.js`，仅在 `-LiveProviders` 时调用真实 Provider，已验证 Codex 新会话首条消息、Claude Sonnet 首条消息、Claude 普通消息历史恢复和恢复后继续发送，共 3 条。
- 回归入口会同时检查 Playwright 退出码、`### Error`、明确的 `{"ok":true}` 结果和 Renderer 控制台错误，避免工具退出码为 0 时误报成功。
- 修复 Claude 历史消息兼容：支持字符串和内容块两种 `content`，命令历史显示为 `/model`，并合并 SDK 返回的重复助手消息。
- 修复 Windows 偏好文件原子替换偶发 `EPERM/EACCES`：只对短暂锁做 5 次有限重试，其他写入错误继续立即失败。
- 完整构建通过：101 项测试中 100 通过、1 项因当前 Windows 用户没有符号链接权限跳过、0 失败；Renderer 初始 JS 仍为 565.52 kB（gzip 172.77 kB），留给 OPT-008。
- 默认核心回归与真实 Provider 回归最终均为 Renderer 控制台 0 错误；脚本结束后 Playwright 会话和 AgentDesk 服务均已关闭。

剩余风险：Windows 符号链接安全用例仍需在具备创建符号链接权限的 CI/开发机执行；真实 Provider 回归会产生少量真实调用，因此默认不启用。

### OPT-005 Provider 事件 controller

从 `App.tsx` 抽出：

- Agent 事件订阅和统一路由。
- 原生会话 ID 与客户端 Tab 的映射。
- Query 代次、迟到事件和子 Agent 归属。
- 高频事件批处理和关键生命周期立即提交。
- Provider 退出后的定向恢复。

验收：Codex/Claude 事件互不污染；旧 Query 事件不能修改新 Query；批处理不延迟审批、完成或错误。

当前结果（2026-08-09，已完成）：

- 新增 `ProviderEventController`，统一持有原生 Thread 到客户端 Session 的映射、子 Agent 归属、提前到达的 Thread 启动事件、事件/生命周期版本和动画帧批处理队列。

- 新增 6 项测试，覆盖生命周期立即提交、高频事件单帧合并、旧 Query 终态丢弃、跨 Provider `clientSessionId` 拒绝绑定、提前启动事件和迟到响应。
- 修复审查时发现的两个风险：旧 Query 的完成事件不再触碰新 Query 的 Pending Steer/队列；直接 Session 绑定必须同时匹配 Provider。
- 完整构建为 119 项中 118 通过、1 项因 Windows 符号链接权限跳过、0 失败；默认 Electron 6 条通过，真实 Provider 3 条通过，Renderer 控制台 0 错误。真实 Provider 首轮曾在测试脚本右键菜单点击处偶发一次元素稳定性超时，原脚本原样重跑通过，未发现产品事件链路异常。
- `App.tsx` 从 OPT-004 完成时的 129,349 字节降到 119,755 字节；`useCallback` 从 89 降到 87，`useRef` 从 27 降到 22。

## 第三阶段：主进程结构

### OPT-007 拆分 `main.ts`

建议模块边界：

- `windowLifecycle`：窗口、托盘、单实例、关闭和激活。

## 每次优化的标准流程

1. 在本文档中选择优先级最高且前置条件满足的一个任务。
2. 记录修改前基线和明确验收条件。
3. 先补缺失测试，再做最小范围实现。
4. 运行完整编译和测试。
5. 按变更范围执行真实 Electron 回归。
6. 检查包体积、控制台错误、进程残留和 Git diff。
7. 更新任务状态、实际指标和剩余风险。
8. 未经用户授权，不提交、不推送、不升版本、不发布。

## 完成定义

一个优化任务只有同时满足以下条件才算完成：

- 目标职责已经从旧模块迁出，旧实现和重复状态已经删除。
- 类型检查、构建和相关自动化测试通过。
- 需要真实 Electron 验证的场景已经实际通过。
- 没有降低安全校验、容量限制或 Provider 隔离。
- 没有用提高警告阈值、隐藏错误或跳过测试替代修复。
- 本文档已更新状态、指标和剩余风险。
